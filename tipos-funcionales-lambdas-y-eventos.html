    7. Tipos funcionales, lambdas y eventos

    En muchos programas hay que pasar a una función no datos, sino un comportamiento: el criterio de ordenación, la condición de filtrado o la acción que debe realizarse cuando ocurre algo. Kotlin responde a esta necesidad tratando las funciones como valores igual que cualquier otro: una función tiene un tipo, el tipo funcional, que se denota, por ejemplo, como [(Int, Int) -> Int]; puede almacenarse en una variable, pasarse como parámetro, devolverse como resultado de otra función y ejecutarse cuando se desee. Una función que recibe o devuelve una función se denomina función de orden superior.

    Java, como recordatorio, no tiene tipos funcionales: se apoya en las interfaces funcionales, interfaces con un único método abstracto ([Runnable], [Comparator], [Function<T, R>]…), y solo a partir de Java 8 (2014) permitió implementarlas mediante expresiones lambda y referencias a métodos. Kotlin admite las lambdas desde su primera versión y también puede trabajar con las interfaces funcionales de Java, ya que utiliza directamente las bibliotecas de Java. Ya hemos usado lambdas ampliamente sin entrar en detalles, en las operaciones sobre colecciones del capítulo 5: en [persons.filter { it.age >= 18 }], pasamos una lambda a la función [filter]. Este capítulo explica qué hay detrás de esta sintaxis. Concluye con los eventos, que Kotlin, al igual que Java, maneja mediante “listeners” (escuchas): funciones, casi siempre lambdas, que se registran en un emisor para ser notificadas de lo que ocurre en él. Las interfaces gráficas de usuario (Swing, JavaFX, Compose) y los frameworks web se basan en este mecanismo: un clic en un botón o la llegada de una solicitud HTTP se notifica a los listeners registrados. Este curso no aborda las interfaces gráficas de usuario; todos los ejemplos son programas de consola.

    Los programas de este capítulo están organizados en el proyecto Gradle [07-lambdas], con un paquete por programa: [src/main/kotlin/lambdas01/Lambdas01.kt], [src/main/kotlin/lambdas02/Lambdas02.kt]… Se ejecutan con [gradlew -q run -Pmain=lambdas01.Lambdas01Kt] o haciendo clic en el triángulo verde de IntelliJ o IDEA. El proyecto no requiere más bibliotecas que la biblioteca estándar de Kotlin: los tipos funcionales, las lambdas y las funciones de alcance están incluidos, y las interfaces del paquete [java.util.function] son las mismas que las del JDK.

    7.1. Tipos funcionales e interfaces funcionales predefinidas

    7.1.1. El concepto de tipo funcional

    Un tipo funcional describe un modelo (también llamado firma o forma) de función: los tipos de sus parámetros, entre paréntesis, seguidos de una flecha y luego del tipo de su valor de retorno. Una variable de tipo funcional puede referirse a cualquier función de esta forma y ejecutarla. A continuación se muestran algunos ejemplos:

    • [() -> Unit]: una función sin parámetros que no devuelve ningún resultado útil ([Unit] cumple el papel del [void] de Java);
    • [() -> String]: una función sin parámetros que devuelve una cadena de caracteres;
    • [(Int) -> Boolean]: una función que recibe un entero y devuelve un booleano, es decir, un predicado;
    • [(Int, Int) -> Int]: una función que recibe dos enteros y devuelve un entero;
    • [(String) -> (Int) -> Int]: una función que recibe una cadena y devuelve… una función de tipo [(Int) -> Int] (la flecha se lee de derecha a izquierda);
    • [(() -> Unit)?]: una función que puede estar ausente; los paréntesis son necesarios porque [() -> Unit?] denotaría, de otro modo, una función que devuelve un [Unit?]. Aquí vemos la propiedad de seguridad frente a [null] del capítulo 3: una función de este tipo se invoca mediante [f?.invoke()];
    • [String.(Int) -> String]: una función con receptor; se aplica a una cadena, que su código denota como [this], como una función de extensión (capítulo 4). Puede llamarse como extensión (["ab".f(3)]) o como una función ordinaria cuyo receptor es el primer parámetro ([f("ab", 3)]).

    Los parámetros pueden nombrarse para documentar el tipo: [(n1: Int, n2: Int) -> Int] es el mismo tipo que [(Int, Int) -> Int].

    Hay tres maneras de obtener un valor de tipo función:

    • escribir una referencia a una función existente que tenga la forma correcta: [val task: () -> Unit = ::display];
    • escribir una expresión lambda: [val task: () -> Unit = { println("task") }];
    • escribir una función anónima: [val task = fun() { println("task") }], o un objeto de una clase que implemente el tipo funcional (un tipo funcional es una interfaz, como veremos). Estas dos notaciones son menos habituales.

    La función se ejecuta entonces como una función ordinaria: [task()]. Es una notación abreviada para llamar al método [invoke] del objeto función: [task.invoke()]. Esta es la primera diferencia notable con Java, donde hay que llamar al método de la interfaz por su nombre ([run], [apply], [test]…); Kotlin se comporta aquí como C#, donde un delegado se llama como un método.

    7.1.2. Tipos funcionales de Kotlin e interfaces de java.util.function

Java 8 introdujo el paquete [java.util.function], que proporciona 43 interfaces funcionales genéricas. Kotlin no las necesita: un tipo funcional se escribe directamente.     Las versiones de Java para tipos primitivos

    En Kotlin no hay un límite práctico para el número de parámetros de un tipo función: [(Int, Int, Int) -> Int] se escribe tan fácilmente como los demás, mientras que en Java, como no existe una interfaz predefinida con tres parámetros, hay que definir una propia.

    ¿Cómo representa la máquina virtual de Java, que solo reconoce clases e interfaces, un tipo funcional? Mediante interfaces genéricas de la biblioteca de Kotlin: [kotlin.jvm.functions.Function0<R>], [Function1<P1, R>], [Function2<P1, P2, R>]… hasta [Function22], y a partir de ahí una interfaz [FunctionN] . Cada una tiene un único método, [invoke]: [(Int, Int) -> Int] se compila en [Function2<Integer, Integer, Integer>], cuyo método es [operator fun invoke(p1: Int, p2: Int): Int]. Es el modificador [operator] de [invoke] (véase la sobrecarga de operadores en el capítulo 4) el que permite la notación [f(2, 3)]. Por lo tanto, un tipo funcional es, para la JVM, una interfaz funcional como las de Java. Dado que los genéricos de Java solo se aplican a tipos de objeto, los valores [Int] pasados a un [(Int, Int) -> Int] se convierten en [Integer] y viceversa (boxing y unboxing). Java evita estas conversiones con sus interfaces especializadas ([IntBinaryOperator]…); Kotlin las evita de otra manera, mediante las funciones [inline], de las que hablaremos más adelante.

import java.util.function.IntBinaryOperator
import java.util.function.Predicate
import java.util.function.Supplier

// tipos de función de Kotlin e interfaces funcionales de Java

fun main() {
    // 1 - () -> Unit: sin parámetros, sin resultado
    val task: () -> Unit = ::display
    // ejecución: la función se llama como una función ordinaria
    task()
    // que es una forma abreviada de llamar a su método invoke
    task.invoke()

    // 2 - (Int, Int) -> Int: dos parámetros, un resultado
    val operation: (Int, Int) -> Int = ::add
    println("operation(2, 3)=${operation(2, 3)}")
    // () -> String: sin parámetros, un resultado
    val greet: () -> String = ::greet
    println("greet()=${greet()}")

    // 3 - (String) -> Unit: un parámetro, sin resultado
    val write: (String) -> Unit = ::println
    write("(String) -> Unit executed println")

    // 4 - (Int) -> Boolean: un predicado
    val isEven: (Int) -> Boolean = ::isEven
    println("isEven(8)=${isEven(8)}")
    val numbers = mutableListOf(3, 8, 1, 6, 5, 4)
    // removeAll de la biblioteca de Kotlin espera un (Int) -> Boolean
    val modified = numbers.removeAll(isEven)
    println("even numbers removed: $modified, remaining: $numbers")

    // 5 - un Comparator<T> (interfaz de Java) construido a partir de una función (conversión SAM)
    val names = mutableListOf("Paul", "Mélanie", "Jo", "Sébastien")
    names.sortWith(Comparator(::compareLengths))
    println("sorted by length: $names")

    // 6 - las interfaces de java.util.function siguen siendo utilizables
    val supplier: Supplier<String> = Supplier(::greet)
    val multiply = IntBinaryOperator(::multiply)
    val predicate = Predicate<Int> { it > 4 }
    println("supplier.get()=${supplier.get()}")
    println("multiply.applyAsInt(2, 3)=${multiply.applyAsInt(2, 3)}")
    // removeIf es un método de Java (Collection): espera un Predicate
    val values = mutableListOf(10, 3, 8, 7, 2, 1)
    values.removeIf(predicate)
    // una función de Kotlin se convierte automáticamente en un Predicate (conversión SAM)
    values.removeIf(isEven)
    values.removeIf { it == 1 }
    println("after removeIf: $values")

    // 7 - un tipo de función que admite null: la función puede estar ausente
    execute(null)
    execute(task)

    // 8 - un tipo de función con receptor: String.(Int) -> String
    val times: String.(Int) -> String = String::repeat
    println("\"ab\".times(3)=${"ab".times(3)}, times(\"cd\", 2)=${times("cd", 2)}")

    // 9 - una función es un objeto, una instancia de una clase que implementa una interfaz
    println("class: ${operation::class.java.name}")
    println("interfaces: ${operation::class.java.interfaces.contentToString()}")
    val sum: (Int, Int) -> Int = { n1, n2 -> n1 + n2 }
    println("class of the lambda: ${sum::class.java.name}")
    println("interfaces: ${sum::class.java.interfaces.contentToString()}")
}

// una función que recibe una función posiblemente ausente
fun execute(callback: (() -> Unit)?) {
    // llamada segura: no se ejecuta nada si callback es null
    callback?.invoke()
    println("callback ${if (callback == null) "absent" else "present"}")
}

    7.2. Definición de tipos funcionales propios

    Los tipos funcionales suelen ser suficientes, pero puede interesar darle un nombre a un modelo de función. Kotlin ofrece dos herramientas para ello, de naturaleza muy diferente.

    La primera es el alias de tipo, declarado con la palabra clave [typealias]:

    • [typealias BinaryOperation = (n1: Int, n2: Int) -> Int]

    Un alias no crea un tipo nuevo: [BinaryOperation] es otro nombre para [(Int, Int) -> Int], y las dos notaciones son intercambiables. El alias hace el código más legible cuando el tipo funcional es largo o aparece con frecuencia.

    La segunda es la interfaz funcional, declarada mediante [fun interface]:

    • [fun interface Operation { fun calculate(n1: Int, n2: Int): Int }]

    Es el equivalente exacto de una interfaz funcional de Java: una interfaz con un solo método abstracto (también conocida como interfaz SAM, o “Single Abstract Method”). También puede tener métodos con cuerpo y propiedades no abstractas; estos no cuentan. La palabra clave [fun] que precede a [interface] cumple la misma función que la anotación de Java [@FunctionalInterface], con una diferencia importante: no es opcional. Es esta palabra clave la que habilita la conversión SAM, es decir, la creación de un objeto [Operation] a partir de una lambda o de una referencia a una función: [Operation { n1, n2 -> n1 + n2 }]. Sin la palabra clave [fun], una interfaz de Kotlin, incluso reducida a un solo método, solo puede ser implementada por una clase o un objeto anónimo ([object : Operation { … }]).

    En comparación con el tipo [(Int, Int) -> Int], el tipo [Operation] es un tipo realmente nuevo, distinto de todos los demás: tiene un nombre que describe su propósito, su método tiene un nombre descriptivo ([calculate] en lugar de [invoke]), puede tener métodos adicionales y puede ser implementado por una clase con nombre. En contrapartida, se ejecuta mediante el nombre de su método ([op.calculate(2, 3)]), y no mediante [op(2, 3)].

    Una variable llamada [op] de tipo [Operation], como una variable de tipo [(Int, Int) -> Int], hace referencia a una sola función a la vez. A diferencia de C#, que ofrece “delegados de multidifusión”, ni Java ni Kotlin permiten almacenar varias funciones en una sola variable y ejecutarlas todas con una sola llamada: cuando es necesario, se almacenan las funciones en una lista y se ejecutan una por una. Es exactamente lo que haremos con los listeners de eventos.

    op = Operation(c1::subtract)

    println("n=$n")

    // una variable referencia una sola función: para ejecutar varias, se usa una lista
    val operations = listOf(
        Operation(c1::add),
        Operation(c1::subtract),
        Operation { n1, n2 -> n1 * n2 },
    )
    for (operation in operations) {
        println("-> ${operation.calculate(10, 4)}")
    }

    // un método de la interfaz construye una nueva operación
    val squaredSum = Operation(c1::add).then { x -> x * x }
    println("squaredSum.calculate(1, 2)=${squaredSum.calculate(1, 2)}")

    // Operation e IntBinaryOperator tienen la misma forma pero son dos tipos diferentes
    val other = IntBinaryOperator(op::calculate)
    println("other.applyAsInt(5, 1)=${other.applyAsInt(5, 1)}")

    // una interfaz funcional genérica
    val length = Transformation(String::length)
    val stars = Transformation("*"::repeat)
    println("length(\"Hello\")=${length.transform("Hello")}")
    println("stars(5)=${stars.transform(5)}")

    // un alias de tipo: simplemente otro nombre para (Int, Int) -> Int
    val f: BinaryOperation = { n1, n2 -> n1 - n2 }
    // BinaryOperation y (Int, Int) -> Int son el mismo tipo
    val g: (Int, Int) -> Int = f
    // pero Operation es un tipo diferente: se necesita una conversión
    val op2 = Operation(g)
    println("f(5, 1)=${f(5, 1)}, g(5, 1)=${g(5, 1)}, op2.calculate(5, 1)=${op2.calculate(5, 1)}")
}

// definición de una interfaz funcional: un único método abstracto
// que recibe dos enteros como parámetros y devuelve un entero
fun interface Operation {
    fun calculate(n1: Int, n2: Int): Int

    // un método con cuerpo no cuenta: la interfaz sigue siendo funcional
    fun then(next: (Int) -> Int): Operation = Operation { n1, n2 -> next(calculate(n1, n2)) }
}

// una interfaz funcional genérica: T -> R
fun interface Transformation<T, R> {
    fun transform(value: T): R
}

// de los objetos anónimos a las expresiones lambda

fun main() {
    // 1 - un objeto anónimo: la clase que implementa el tipo de función se escribe en el lugar
    val add = object : (Int, Int) -> Int {
        override fun invoke(n1: Int, n2: Int): Int {
            return n1 + n2
        }
    }
    println("anonymous object: add(2, 3)=${add(2, 3)}")

    // 2 - lo mismo con una expresión lambda: { parámetros -> cuerpo }
    val subtract = { n1: Int, n2: Int -> n1 - n2 }
    println("lambda with typed parameters: subtract(2, 3)=${subtract(2, 3)}")

    // 3 - los tipos de los parámetros se infieren del tipo esperado
    val multiply: (Int, Int) -> Int = { n1, n2 -> n1 * n2 }
    println("lambda with untyped parameters: multiply(2, 3)=${multiply(2, 3)}")

    // 4 - un solo parámetro: no es necesario nombrarlo, entonces se llama it
    val square: (Int) -> Int = { it * it }
    val isEmpty: (String) -> Boolean = { s -> s.isEmpty() }
    println("square(7)=${square(7)}, isEmpty(\"\")=${isEmpty("")}")

    // 5 - sin parámetros: sin flecha
    val greet = { "Hello" }
    val beep = { println("beep!") }
    println(greet())
    beep()

    // 6 - un cuerpo de varias instrucciones: el valor de la última expresión es el resultado
    val repeat: (String, Int) -> String = { text, times ->
        val buffer = StringBuilder()
        for (i in 1..times) {
            buffer.append(text)
        }
        buffer.toString()
    }
    println(repeat("ab", 3))

    // 7 - parámetros no utilizados: _
    val listener: (Any?, String) -> Unit = { _, _ -> println("event received") }
    listener(null, "click")

    // 8 - una lambda pasada como parámetro: fuera de los paréntesis si es el último parámetro
    val numbers = mutableListOf(3, 8, 1, 6, 5, 4)
    val evens = numbers.filter { it % 2 == 0 }
    println("evens: $evens")
    numbers.sortWith { n1, n2 -> n2.compareTo(n1) }
    println("descending order: $numbers")
    // la lambda fuera de los paréntesis, después de otros parámetros
    val total = numbers.fold(0) { acc, n -> acc + n }
    println("total: $total")

    // 9 - return en una lambda: return@label sale solo de la lambda
    numbers.forEach {
        if (it % 2 == 0) return@forEach
        print("$it ")
    }
    println("<- odds")
    // una etiqueta elegida por el desarrollador
    numbers.forEach odd@{ n ->
        if (n % 2 != 0) return@odd
        print("$n ")
    }
    println("<- evens")
    // una función anónima: return allí sale de la función anónima
    val isLarge = fun(n: Int): Boolean {
        if (n > 5) return true
        return false
    }
    println("large: ${numbers.filter(isLarge)}")

    // 10 - desestructuración de los parámetros de una lambda
    val ages = mapOf("Paul" to 40, "Mélanie" to 35)
    ages.forEach { (name, age) -> println("$name is $age years old") }

    • líneas 7–12: un objeto anónimo. La palabra clave [object] va seguida de dos puntos y del tipo que se va a implementar, en este caso el tipo funcional [(Int, Int) -> Int] (es una interfaz, como hemos visto), y del cuerpo de una clase que implementa este tipo redefiniendo su método [invoke]. El compilador genera una clase sin nombre y crea una instancia de ella. Seis líneas para expresar [n1 + n2]. Aun así, se ejecuta como una función: [add(2, 3)];
    • línea 15: lo mismo con una expresión lambda. Una lambda se escribe entre llaves: la lista de parámetros, el operador [->] (una flecha, que se lee “da”), y luego el cuerpo. El nombre del tipo y el nombre del método han desaparecido. Como los parámetros tienen tipo, el compilador puede determinar por sí solo el tipo de la lambda: [(Int, Int) -> Int]. Esto difiere de Java, donde una lambda nunca tiene un tipo propio;
    • línea 19: se han omitido los tipos de los parámetros. El compilador los infiere a partir del tipo esperado declarado para la variable: [n1] y [n2] son de tipo [Int]. Esta es la forma más común. En Kotlin no hay distinción entre un “cuerpo de expresión” y un “cuerpo de bloque”, como ocurre en Java: el cuerpo de una lambda es una secuencia de instrucciones, y el valor de la última expresión es el resultado de la lambda;
    • Línea 23: con un solo parámetro, no es necesario declararlo, ni tampoco la flecha; entonces se llama implícitamente [it] (“it”, “eso”). [{ it * it }] se lee “su cuadrado”. Línea 24: el único parámetro se llama [s]. Esto se hace cuando [it] haría el código menos legible, en particular cuando las lambdas están anidadas (cada una tendría su propio [it]);
    • Líneas 28–29: sin parámetros, no hay flecha. El tipo de *[greet]* se infiere como *[() -> String]*; el tipo de *[beep] es *[() -> Unit]*, ya que *[println] produce *[Unit]*;
    • Líneas 34–39: una lambda puede contener cualquier instrucción: declaraciones, bucles, condicionales, etc. El valor de la última expresión, [buffer.toString()], es el resultado. No se puede escribir [return buffer.toString()]: en una lambda, un [return] sin etiqueta no sale de la lambda (véase más adelante);
    • línea 44: el carácter de subrayado [_] denota un parámetro no utilizado. Se usa cuando la firma del tipo exige parámetros que la lambda no necesita, lo cual es habitual en los listeners de eventos. Se pueden incluir varios de estos parámetros en la misma lambda (Java adoptó esta sintaxis en la versión 22);
    • Líneas 48–49: el uso más común de las lambdas es pasarlas directamente como parámetros a una función de orden superior. Cuando la lambda es el último parámetro, se escribe fuera de los paréntesis; si no hay otros parámetros, se omiten los paréntesis: [numbers.filter { it % 2 == 0 }] en lugar de [numbers.filter({ it % 2 == 0 })]. Esta regla es la que da al código Kotlin su aspecto característico y permite escribir funciones que se parecen a instrucciones del lenguaje ([repeat], [use], [thread], [synchronized]…). Compárese con [Lambdas01.kt]: ya no es necesario escribir una función [isEven];
    • línea 51: una lambda que invierte la comparación habitual: la lista se ordena de forma descendente. [sortWith] espera un [Comparator] (una interfaz de Java): la conversión a SAM se realiza automáticamente;
    • línea 54: la lambda permanece fuera de los paréntesis cuando la función tiene otros parámetros: [fold(0) { acc, n -> acc + n }]. La función [fold] (capítulo 5) parte del valor inicial 0 y suma los elementos uno por uno;
    • líneas 58–62: dentro de una lambda, la instrucción [return@forEach] sale de la lambda (y pasa así al elemento siguiente), igual que un [continue] en un bucle. La etiqueta [@forEach] es implícita: es el nombre de la función a la que se pasa la lambda. Un [return] sin etiqueta saldría de toda la función [main]: esto se denomina retorno no local, y solo se permite en una lambda pasada a una función como [inline] o [forEach] (veremos por qué);
    • líneas 64–68: también puede elegirse la etiqueta colocándola antes de la llave de apertura: [odd@{ … }], luego [return@odd];
    • líneas 70–74: una función anónima. Se escribe como una función normal, pero sin nombre. Su tipo se infiere: [(Int) -> Boolean]. En una función anónima, [return] sale de la propia función anónima. Se usa cuando el cuerpo tiene varios puntos de salida, o cuando se desea especificar explícitamente el tipo del resultado;
    • Línea 78: los parámetros de una lambda pueden desestructurarse (capítulo 3). La lambda pasada a [forEach] recibe una entrada del arreglo asociativo ([Map.Entry<String, Int>]); la notación [(name, age)], entre paréntesis, la descompone en su clave y su valor. Atención: [{ name, age -> … }] declararía dos parámetros, mientras que [{ (name, age) -> … }] declararía un único parámetro desestructurado.

    Una lambda no es exactamente una abreviatura de un objeto anónimo. En un objeto anónimo, [this] hace referencia al propio objeto anónimo; en una lambda, [this] hace referencia al objeto del método que contiene la lambda (o al receptor, en el caso de una lambda con receptor). Además, un objeto anónimo puede implementar una interfaz con varios métodos, varias interfaces a la vez, o heredar de una clase, lo cual es imposible con una lambda. En este curso utilizaremos lambdas siempre que sea posible.

import java.util.concurrent.Callable

// más sobre lambdas y referencias

fun main() {
    // 1 - el tipo de una lambda se infiere de sus parámetros y su cuerpo...
    val double = { x: Int -> x * 2 }
    println("double(21)=${double(21)}")
    // ... o lo fija el tipo esperado: el mismo texto de lambda puede dar tres tipos diferentes
    val function: () -> String = { "Hello" }
    val supplier = Supplier { "Hello" }
    val callable = Callable { "Hello" }
    println("${function()} / ${supplier.get()} / ${callable.call()}")

    // 2 - los tipos de referencias
    // a) función de nivel superior: ::function
    val triple: (Int) -> Int = ::triple
    println("triple(14)=${triple(14)}")
    // b) método o propiedad de un objeto dado (referencia vinculada): object::method
    val name = "Pierre"
    val inUpperCase: () -> String = name::uppercase
    val nameLength: () -> Int = name::length
    println("inUpperCase()=${inUpperCase()}, nameLength()=${nameLength()}")
    // c) método de cualquier objeto de la clase (referencia no vinculada): Class::method
    //    el objeto sobre el que se llama el método pasa a ser el primer parámetro
    val upperCase: (String) -> String = String::uppercase
    val ignoreCase: (String, String) -> Int = { s1, s2 -> s1.compareTo(s2, ignoreCase = true) }
    println("upperCase(\"paul\")=${upperCase("paul")}")
    println("ignoreCase(\"abc\", \"ABC\")=${ignoreCase("abc", "ABC")}")
    // d) función de extensión: Class::extension
    val convert: (String) -> Int = String::toInt
    println("convert(\"42\") + 1 = ${convert("42") + 1}")
    // e) constructor: ::Class
    val createList: () -> MutableList<String> = ::ArrayList
    val createBuffer: (String) -> StringBuilder = ::StringBuilder
    val createArray: (Int) -> IntArray = ::IntArray
    val createPerson: (String, Int) -> Person = ::Person
    val list = createList()
    list.add("element")
    println("$list ${createBuffer("abc").reverse()} ${createArray(3).size} ${createPerson("Paul", 40)}")

    // 3 - sin excepciones verificadas: cualquier lambda puede lanzar cualquier excepción
    val read: () -> Int = { throw IOException("file missing") }
    try {
        read()
    } catch (ex: IOException) {
        println("exception received: ${ex.message}")
    }

    // 4 - igualdad de funciones: las referencias son comparables, las lambdas no
    val r1: () -> String = name::uppercase
    val r2: () -> String = name::uppercase
    val l1 = { name.uppercase() }
    val l2 = { name.uppercase() }
    println("r1 == r2 : ${r1 == r2}, r1 === r2 : ${r1 === r2}, l1 == l2 : ${l1 == l2}")
}

import java.util.function.Function

// composición de funciones: funciones que devuelven funciones

fun main() {
    // 1 - composición: nuestras extensiones then (primero this, luego la otra) y after (primero la otra)
    val plusOne: (Int) -> Int = { it + 1 }
    val timesTwo: (Int) -> Int = { it * 2 }
    println("(plusOne then timesTwo)(5)=${(plusOne then timesTwo)(5)}")
    println("(plusOne after timesTwo)(5)=${(plusOne after timesTwo)(5)}")
    // los métodos de la interfaz Function de Java siguen disponibles
    val f = Function<Int, Int> { it + 1 }.andThen { it * 2 }
    println("Function.andThen: f.apply(5)=${f.apply(5)}")
    // una función que fabrica funciones
    val plusTen = adder(10)
    println("adder(10)(5)=${plusTen(5)}, adder(3)(5)=${adder(3)(5)}")
    // una cadena de procesamiento construida a partir de una lista de funciones
    val steps: List<(String) -> String> = listOf(String::trim, String::lowercase, { it.replace(' ', '-') })
    val normalize = steps.fold({ s: String -> s }) { function, step -> function then step }
    println("normalize(\"  My Nice Title \")=${normalize("  My Nice Title ")}")

    // 2 - predicados: nuestras extensiones and, or, not
    val short: (String) -> Boolean = { it.length <= 4 }
    val startsWithP: (String) -> Boolean = { it.startsWith("P") }
    val firstNames = listOf("Paul", "Mélanie", "Jo", "Sébastien", "Pierre")
    println("short and P: ${filterElements(firstNames, short and startsWithP)}")
    println("short or P: ${filterElements(firstNames, short or startsWithP)}")
    println("not short: ${filterElements(firstNames, !short)}")
    // un predicado sobre CharSequence sirve para filtrar Strings
    val notEmpty: (CharSequence) -> Boolean = { it.isNotEmpty() }
    println("not empty: ${filterElements(listOf("a", "", "b"), notEmpty)}")

    // 3 - varios procesamientos del mismo valor
    val log = mutableListOf<String>()
    val display: (String) -> Unit = { println("display: $it") }
    val remember: (String) -> Unit = { log.add(it) }
    val both = display andAlso remember
    both("first")
    both("second")
    println("log: $log")

    // 4 - comparadores: compareBy, thenBy, thenByDescending, reversed
    val persons = mutableListOf(Person("Paul", 32), Person("Mélanie", 25),
        Person("Jo", 32), Person("Sébastien", 25))
    persons.sortWith(compareBy(Person::age).thenBy(Person::name))
    println("by age then name: $persons")
    persons.sortWith(compareBy(Person::age).reversed().thenByDescending(Person::name))
    println("by descending age then descending name: $persons")
    // varios criterios a la vez
    persons.sortWith(compareBy({ it.name.length }, { it.name }))
    println("by name length then name: $persons")
    // un comparador también se usa para elegir el menor de dos elementos
    val byAge = compareBy(Person::age)
    println("younger of Paul and Mélanie: ${minOf(persons[1], persons[2], byAge)}")
}

fun <T> filterElements(elements: List<T>, predicate: (T) -> Boolean): List<T> {
    val result = mutableListOf<T>()
    for (element in elements) {
        if (predicate(element)) {
            result.add(element)
        }
    }
    return result
}

fun main() {

    println("variableThreshold=$variableThreshold : exceedsVariable(7)=${exceedsVariable(7)}")

    variableThreshold = 10
    println("variableThreshold=$variableThreshold : exceedsVariable(7)=${exceedsVariable(7)}")

    // 3 - una lambda puede modificar una variable local capturada
    var total = 0
    val accumulate: (Int) -> Unit = { n -> total += n }
    accumulate(3)
    accumulate(4)
    println("total=$total")
    // la variable capturada se almacena en un objeto Ref, que la lambda conserva
    println("fields of the lambda: ${accumulate::class.java.declaredFields.map { it.type.name }}")
    // una variable de nivel superior (o una propiedad) también puede modificarse
    val count = { nbCalls++ }
    count()
    count()
    println("nbCalls=$nbCalls")

    // 4 - un closure: la variable capturada sobrevive a la función que la creó
    val counterA = createCounter()
    val counterB = createCounter()
    println("A: ${counterA()} ${counterA()} ${counterA()}")
    println("B: ${counterB()} ${counterB()}")

    // 5 - el bucle for declara una nueva variable i en cada iteración
    val actions = mutableListOf<() -> Unit>()
    for (i in 0..2) {
        actions.add { print("$i ") }
    }
    print("for: ")
    actions.forEach { it() }
    println()

    // la trampa: todas las lambdas comparten la misma var
    actions.clear()
    var k = 0
    while (k < 3) {
        actions.add { print("$k ") }
        k++
    }
    print("while, capture of the var k: ")
    actions.forEach { action -> action() }
    println()
}

    La regla de Java tiene una justificación sólida: una lambda puede ejecutarse más tarde, o en otro hilo (capítulo 8). Si puede modificar las variables locales de una función, o leerlas mientras otro hilo las modifica, esto puede provocar un comportamiento impredecible. Kotlin adopta un enfoque diferente y más práctico: capturar [var] está permitido, pero los objetos [Ref] no están protegidos contra el acceso concurrente. Por lo tanto, recordemos que capturar un [var] es seguro en un programa de un solo hilo y en lambdas que se ejecutan de inmediato ([forEach], [filter]…), pero que, en cuanto una lambda puede ejecutarse en otro hilo, el estado mutable compartido debe hacerse explícito mediante un objeto cuyo comportamiento respecto de los hilos se elija explícitamente ([AtomicInteger], colección concurrente…). Volveremos sobre este tema en los capítulos 8 y 9. Las funciones [inline], que se presentan más adelante, también evitan la creación de objetos [Ref] cuando el código de la lambda se copia en el código que llama.

    7.4. Funciones inline y funciones de alcance

    7.4.1. Funciones inline

    Una lambda es un objeto. Por lo tanto, pasar una lambda a una función de orden superior tiene un costo: la creación del objeto (excepto en el caso de una lambda que no captura nada, que la máquina virtual puede reutilizar), la llamada a su método [invoke] , las conversiones [Int] ↔ [Integer] impuestas por las interfaces genéricas [Function1], [Function2]…, y los objetos [Ref] de las variables capturadas. Para una función como [filter], que se llama sobre cada elemento de colecciones que a veces pueden ser muy grandes, este costo importa. Kotlin lo elimina con el modificador [inline]: cuando una función se declara [inline fun], el compilador no genera una llamada a esa función; en su lugar, copia su código en cada lugar donde se la llama, y copia también el código de las lambdas que se le pasan. Como resultado, ya no hay objetos lambda, ni llamadas a [invoke], ni conversiones. Las funciones de la biblioteca estándar que aceptan lambdas ([forEach], [filter], [map], [fold], [let], [apply], [repeat], [use], [synchronized]…) son casi todas [inline]. Java no tiene un equivalente: confía en el compilador just-in-time de la máquina virtual para producir un resultado comparable en tiempo de ejecución.

    La inserción del código tiene una segunda consecuencia, más notoria: como el código de la lambda se copia en la función que llama, una instrucción [return] sin etiqueta puede salir desde allí de la función que llama. Este es el retorno no local que encontramos con *[forEach] en *[Lambdas03.kt]. Dos modificadores complementan a *[inline]*:

    • [noinline], aplicado a un parámetro de función de una función [inline], especifica que la lambda correspondiente no debe copiarse, sino pasarse como un objeto normal. Esto es necesario cuando la función quiere conservar la lambda (almacenarla en una lista, devolverla como resultado, etc.): el código copiado no se puede almacenar en una lista;
    • [crossinline] exige que la lambda se copie, pero prohíbe los retornos no locales. Esto es necesario cuando la función [inline] no ejecuta la lambda por sí misma, sino en otro contexto, por ejemplo, dentro de un objeto [Runnable] que ella crea: cuando [Runnable] se ejecuta, la función que llama puede haber terminado hace mucho tiempo, y un [return] ya no podría salir de ella.

fun firstEven(numbers: List<Int>): Int? {

inline fun executeThenStore(

    immediate: () -> Unit,
    noinline stored: () -> Unit,

    7.4.2. Funciones de alcance

    La biblioteca estándar de Kotlin proporciona cinco funciones pequeñas y muy utilizadas, [inline], conocidas como “funciones de alcance” (scope functions): [let], [run], [with], [apply] y [also]. Casi no hacen nada: cada una ejecuta una lambda sobre un objeto. Se diferencian en dos aspectos:

    • la forma en que la lambda hace referencia al objeto: ya sea como su parámetro [it] (la lambda es de tipo [(T) -> R]), o como su receptor [this], que entonces puede omitirse (la lambda es una lambda con receptor, de tipo [T.() -> R]; véase [Lambdas01.kt]);
    • que es lo que devuelve la función: o bien el resultado de la lambda, o bien el propio objeto.

// las funciones de alcance (scope functions): let, run, with, apply, also (y takeIf)

fun main() {
    // 1 - apply: configura el objeto (this) y devuelve el objeto
    val paul = Person("Paul").apply {
        age = 32
        city = "Angers"
    }
    println("apply: $paul")

    // 2 - also: un procesamiento adicional del objeto (it), que se devuelve
    val persons = mutableListOf<Person>()
    val melanie = Person("Mélanie", 25).also { persons.add(it) }
    println("also: $melanie, persons=$persons")

    // 3 - let: transforma el objeto (it) en un resultado; muy usado con ?.
    val length = paul.name.let { it.length * 2 }
    println("let: length=$length")
    for (city in listOf("Tours", null)) {
        val message = city?.let { "lives in ${it.uppercase()}" } ?: "unknown city"
        println("let and ?.: $message")
    }

    // 4 - run: un cálculo sobre el objeto (this), que devuelve un resultado
    val description = paul.run { "$name, $age years old, lives in $city" }
    println("run: $description")

    // 5 - with: como run, pero el objeto se pasa como parámetro
    val summary = with(StringBuilder()) {
        append("Persons: ")
        append(persons.joinToString { it.name })
        toString()
    }
    println("with: $summary")

    // 6 - takeIf: el objeto si cumple el predicado, null en caso contrario
    for (age in listOf(15, 40)) {
        val adult = Person("Jo", age).takeIf { it.age >= 18 }
        println("takeIf: ${adult ?: "minor"}")
    }
}

class Person(val name: String, var age: Int = 0) {
    var city: String? = null

    override fun toString() = "Person(name=$name, age=$age, city=$city)"

    Estos dos ejemplos muestran que en Kotlin, al igual que en Java, una función que espera un comportamiento acepta objetos de clases escritas para ese fin, referencias y lambdas. Quedan dos preguntas. La primera es específica de Kotlin: para un parámetro funcional, ¿es obligatorio un tipo funcional o basta con una [fun interface]?

    • El tipo funcional es la opción predeterminada. No requiere declaración, se llama como una función, acepta directamente lambdas y referencias, y se beneficia de las funciones [inline]. Un [typealias] le da un nombre cuando es largo;
    • la interfaz “fun” se justifica cuando se desea un tipo verdaderamente distinto (que no pueda confundirse con otra función de la misma forma), un método con un nombre descriptivo, métodos adicionales con cuerpo, o una API destinada también a quienes llaman desde Java: para Java, una [fun interface] es una interfaz funcional ordinaria, utilizable con sus lambdas, mientras que un tipo funcional de Kotlin se le presenta como una [Function2<Integer, Integer, Integer>] cuyo método [invoke] debe devolver un objeto ([Unit] para una función “sin retorno”).

    La segunda pregunta es la misma que en Java: ¿la interfaz debe tener un solo método o varios?

    • Una función, un tipo funcional o una interfaz de un solo método es más flexible de usar: sirve cualquier función existente con la forma correcta, y una lambda permite incluso escribir la función justo donde se llama. No hay que escribir ninguna clase. Esta flexibilidad explica por qué las bibliotecas modernas (colecciones, las corrutinas del capítulo 9, Spring) usan ampliamente parámetros funcionales;
    • una interfaz con varios miembros recupera la ventaja en cuanto el comportamiento que se debe implementar involucra varias operaciones relacionadas entre sí ([calculate] y [name] más arriba), o cuando requiere su propio estado e identidad.

    Es el caso de la interfaz [ITaxDao] en la capa [dao] del capítulo 6: aunque solo tiene un miembro (la propiedad [val taxBrackets: List<TaxBracket>]), sus implementaciones tienen estado (los tramos leídos, el nombre del archivo), las crea el contenedor de inyección de dependencias y representan un rol claramente nombrado dentro de la aplicación. Un [() -> List<TaxBracket>] habría bastado técnicamente, pero habría sido mucho menos descriptivo. Por lo tanto, reservamos los tipos funcionales para comportamientos breves y puntuales (un criterio, una transformación, una acción), y las interfaces “de negocio” para los roles de la aplicación, sin importar el número de sus miembros.

    7.6. Manejo de eventos

    7.6.1. El patrón Observador

    Las funciones pasadas como parámetros se utilizan para implementar eventos. Al igual que Java, Kotlin no tiene una palabra clave dedicada a los eventos (C# tiene la suya, [event]): utiliza las convenciones establecidas por Java desde la versión 1.1 para los componentes gráficos y los JavaBeans, conocidas como el “modelo de escuchas”. Una clase [C1] que quiere señalar un evento [Xxx] procede de la siguiente manera:

    • Una clase [XxxEvent] encapsula la información sobre el evento, incluido el objeto que lo desencadenó, conocido como la fuente. En Java, la convención es que derive de [java.util.EventObject], que almacena la fuente; en Kotlin basta con una clase normal con propiedades de solo lectura, y eso es lo que haremos;
    • Un tipo de escucha define la forma de la función que se llamará cuando ocurra el evento. En Java, es una interfaz llamada [XxxListener]; en Kotlin, suele ser un simple tipo funcional, [(XxxEvent) -> Unit], nombrado mediante un [typealias]: una escucha será una lambda o una referencia a función;
    • la clase [C1] administra una lista de funciones y ofrece dos métodos públicos para registrarse y darse de baja en ella: [addXxxListener(listener)] y [removeXxxListener(listener)];
    • Cuando una instancia [c1] de [C1] quiere señalar el evento, crea un objeto [XxxEvent] y llama a cada una de las escuchas registradas, pasándoles este objeto. Por convención, esta notificación la gestiona un método protegido [fireXxx(e: XxxEvent)] (“disparar”), que una clase derivada puede sobrescribir para modificar la forma en que se publica el evento;
    • Si un objeto [c2] quiere ser notificado del evento [Xxx] del objeto [c1], se suscribe mediante [c1.addXxxListener(...)]. Puede darse de baja con [c1.removeXxxListener(...)] cuando ya no desea ser notificado. Dado que [c1] administra una lista, distintos objetos pueden suscribirse para ser notificados del mismo evento.

    En este escenario, tenemos:

    • una clase que señala (también se dice “publica” o “emite”) un evento;
    • objetos que son notificados de este evento. Se dice que se suscriben o se registran al evento: son las escuchas, o manejadores de eventos;
    • un tipo de escucha que define la forma de las funciones que serán notificadas del evento.

    Este es el patrón de diseño Observador: el emisor no conoce a sus suscriptores; simplemente los notifica. Este modelo ofrece la misma protección que una palabra clave dedicada: la lista de escuchas es una propiedad privada del emisor. Desde el exterior, solo se puede suscribir o darse de baja; no se puede vaciar la lista, reemplazar otras escuchas ni disparar el evento en lugar del emisor.

La información sobre este evento se encapsulará en un objeto [TemperatureTooHighEvent], y las escuchas serán funciones de tipo [TemperatureTooHighListener];

    • Un programa de consola crea un emisor y dos suscriptores. Ingresa temperaturas por el teclado y las registra en el emisor. Si alguna es demasiado alta, el emisor señala el evento [TemperatureTooHigh].

    • Línea 18: el tipo de la escucha. Una escucha es una función que recibe el objeto del evento como argumento y no devuelve nada. Mientras que Java exige una interfaz *[TemperatureTooHighListener]* derivada de *[EventListener]*, Kotlin simplemente usa un alias de tipo funcional. Podríamos haber declarado igualmente una ***[fun interface TemperatureTooHighListener]***: sería la elección correcta si las escuchas se fueran a escribir en Java;

Esta lista es el tipo estándar para listas de escuchas: la lista se recorre en cada evento, pero rara vez se modifica;
    • Líneas 31–36: la propiedad [temperature] tiene un descriptor de acceso [set] personalizado (capítulo 4): almacena el nuevo valor en el campo oculto [field] y luego señala el evento si supera el umbral. La publicación está a cargo del método [fireTemperatureTooHigh], al que se le pasa un objeto [TemperatureTooHighEvent]; este objeto proviene del propio emisor ([this]) y contiene la temperatura que superó el umbral. Mientras que Java exige un método llamado [setTemperature], quien usa la clase simplemente escribe [e1.temperature = 21.0];
    • líneas 41–42: registrar una escucha la agrega a la lista. El tipo del parámetro no admite nulos: el compilador rechaza cualquier escucha de tipo [null], algo que Java debe rechazar en tiempo de ejecución mediante [Objects.requireNonNull];

    • líneas 51–53: la notificación llama a cada escucha registrada, en el orden en que se registraron, como una función: [listener(e)]. Si no hay escuchas, el bucle no hace nada: no hay casos especiales que manejar.

// una clase que se registra como escucha del evento
class Subscriber(
    // nombre del suscriptor
    private val name: String,
    // número máximo de alertas aceptadas
    private val nbMaxAlerts: Int,
) {
    // número de alertas recibidas
    private var nbAlerts = 0

    // registro en un emisor
    fun subscribe(emitter: Emitter) {
        emitter.addTemperatureTooHighListener(::onTemperatureTooHigh)
    }

    // cancelación del registro: una nueva referencia al mismo método del mismo objeto es igual a ella
    fun unsubscribe(emitter: Emitter) {
        emitter.removeTemperatureTooHighListener(::onTemperatureTooHigh)
    }

    // manejador del evento TemperatureTooHigh
    private fun onTemperatureTooHigh(e: TemperatureTooHighEvent) {
        val emitter = e.source
        val temperature = "%.1f".format(e.temperature)
        println("Subscriber [$name]: the source [${emitter.name}] " +
            "signaled a temperature that is too high: [$temperature]")
        // más allá de nbMaxAlerts alertas, el suscriptor cancela su registro
        nbAlerts++
        if (nbAlerts == nbMaxAlerts) {
            unsubscribe(emitter)
            println("Subscriber [$name]: unsubscribed after $nbAlerts alert(s)")
        }
    }
}

    • líneas 14–15: registro ante un emisor. La escucha es una referencia enlazada, [::onTemperatureTooHigh], es decir, [this::onTemperatureTooHigh]: el método de este suscriptor, [onTemperatureTooHigh];
    • líneas 19–20: darse de baja pasa una nueva referencia, [::onTemperatureTooHigh], a [removeTemperatureTooHighListener]. En Java, este sería un error clásico: dos evaluaciones de [this::onTemperatureTooHigh] producen dos objetos que [equals]* considera distintos, y la baja no eliminaría nada, sin ningún mensaje de error; la escucha debe crearse una sola vez y almacenarse en un campo. Vimos con [Lambdas04.kt] que en Kotlin dos referencias a la misma función del mismo objeto son iguales: [remove] encuentra por lo tanto la escucha registrada, y solo esa, ya que las referencias de los demás suscriptores están enlazadas a otros objetos. No sucedería lo mismo con una lambda: [{ e -> onTemperatureTooHigh(e) }]*, escrita dos veces, daría como resultado dos objetos distintos;
    • Línea 24: el manejador del evento. Tiene la forma dictada por el tipo [TemperatureTooHighListener]. Es privado: solo el suscriptor puede registrarlo ante un emisor. Otro enfoque consiste en que la propia clase [Subscriber] implemente el tipo de escucha ([class Subscriber : TemperatureTooHighListener], con un método [invoke]) y se registre con [this]. Este enfoque tiene el inconveniente de hacer público el método [invoke], que cualquiera podría entonces llamar;
    • línea 25: la fuente del evento es directamente de tipo [Emitter];
    • líneas 26–28: el manejador muestra el nombre del suscriptor, el nombre del emisor que informó del evento y la temperatura que lo desencadenó. El formato [%.1f] muestra el número real con un decimal, según las convenciones locales de la máquina (la función [format] de Kotlin las utiliza; aquí, un punto decimal). La cadena se escribe en dos partes concatenadas mediante [+] para que la línea quepa en la página;

    7.6.3. Eventos de cambio de propiedad

    El tipo de evento más común se produce cuando una propiedad de un objeto cambia de valor: otro objeto (una interfaz gráfica de usuario, una caché, un registro) quiere ser notificado de este cambio. Kotlin y la biblioteca de Java ofrecen dos herramientas complementarias para este escenario:

    • las propiedades delegadas de Kotlin. Una propiedad declarada como [var p: T by delegate] delega la lectura y la escritura de su valor en otro objeto, el delegado. La biblioteca estándar proporciona varios, como [by lazy { … }], que calcula el valor de la propiedad en el primer acceso. El objeto [kotlin.properties.Delegates] proporciona dos delegados que aceptan una lambda: [Delegates.observable(initialValue) { property, old, new -> … }] ejecuta la lambda después de cada escritura en la propiedad; [Delegates.vetoable(initialValue) { property, old, new -> … }] la ejecuta antes y acepta el nuevo valor solo si la lambda devuelve [true]. El parámetro [property] es una referencia a la propiedad ([KProperty]), cuyo nombre se obtiene mediante [property.name];
    • la clase de Java [java.beans.PropertyChangeSupport], que administra por nosotros la lista de escuchas. Las escuchas implementan la interfaz funcional [PropertyChangeListener], cuyo método [void propertyChange(PropertyChangeEvent evt)] recibe un evento que contiene la fuente, el nombre de la propiedad y sus valores anterior y nuevo.

class Thermometer(name: String) {
    // la gestión de escuchas se delega en un objeto PropertyChangeSupport
    private val changes = PropertyChangeSupport(this)

    // una propiedad observable: después de cada escritura, se señala el cambio
    private fun <T> observable(initialValue: T): ReadWriteProperty<Any?, T> =
        Delegates.observable(initialValue) { property, old, new ->
            changes.firePropertyChange(property.name, old, new)
        }

    var name: String by observable(name)
    var temperature: Double by observable(0.0)

    // una propiedad que rechaza los valores fuera del intervalo [5, 30]
    var setpoint: Double by Delegates.vetoable(20.0) { _, _, new -> new in 5.0..30.0 }

    // registro y cancelación del registro de los escuchas
    fun addPropertyChangeListener(listener: PropertyChangeListener) {
        changes.addPropertyChangeListener(listener)
    }

    fun addPropertyChangeListener(property: String, listener: PropertyChangeListener) {
        changes.addPropertyChangeListener(property, listener)
    }

    fun removePropertyChangeListener(listener: PropertyChangeListener) {
        changes.removePropertyChangeListener(listener)
    }

    val nbListeners: Int
        get() = changes.propertyChangeListeners.size

Por último, cabe señalar que, para los flujos de eventos asíncronos, Kotlin ofrece el [Flow] de la biblioteca kotlinx.coroutines, que veremos en el capítulo 9 ([StateFlow], en particular, actúa como una propiedad observable).

    7.7. Lambdas, colecciones y secuencias

    En el capítulo 5 usamos las operaciones funcionales de las colecciones ([filter], [map], [sortedBy]…) y de las secuencias pasándoles lambdas. Ahora sabemos qué son estos parámetros: la función [filter] se declara así en la biblioteca estándar: [inline fun <T> Iterable<T>.filter(predicate: (T) -> Boolean): List<T>].

// lambdas, colecciones y secuencias

fun main() {
    val numbers = listOf(3, 8, 1, 6, 5, 4, 9, 2)

    // 1 - filter y map esperan funciones (T) -> Boolean y (T) -> R
    val isEven: (Int) -> Boolean = { it % 2 == 0 }
    val square: (Int) -> Int = { it * it }
    println("collections: ${numbers.filter(isEven).map(square)}")
    // la API Stream de Java sigue siendo utilizable: las lambdas se convierten en Predicate y Function
    println("Stream: ${numbers.stream().filter { it % 2 == 0 }.map { it * it }.toList()}")

    // 2 - nuestra propia función de filtrado, llamada con una lambda y luego con una referencia
    println("filterBy(n > 4): ${numbers.filterBy { it > 4 }}")
    println("filterBy(isOdd): ${numbers.filterBy(::isOdd)}")

    // 3 - una colección se evalúa de inmediato: cada paso produce una lista completa
    val largeList = numbers.filter {
        print("[test $it] ")
        it > 7
    }
    println()
    println("the list is already computed: $largeList")

    // 4 - una secuencia se evalúa bajo demanda:
    //     el predicado solo lo llama la operación terminal
    val large = numbers.asSequence().filter {
        print("[test $it] ")
        it > 7
    }
    println("the sequence is defined, nothing has been executed yet")
    large.forEach { print("-> $it ") }
    println()

    // 5 - nuestras propias operaciones intermedias sobre secuencias, también perezosas
    val cities = listOf("Angers", "Paris", "Lyon", "Nantes", "Aix")
    val result = cities.asSequence()
        .keep { it.length <= 5 }
        .transform(String::uppercase)
        .toList()
    println("our operations: $result")
    // una secuencia infinita: solo se calculan los elementos solicitados
    val powersOfTwo = generateSequence(1) { it * 2 }
    val firstOnes = powersOfTwo.transform { "2^${it.countTrailingZeroBits()}=$it" }.take(5)
    println("powers of 2: ${firstOnes.toList()}")
}

// filtra una lista con un predicado: el trabajo que hace filter
inline fun <T> List<T>.filterBy(predicate: (T) -> Boolean): List<T> {
    val result = mutableListOf<T>()
    for (element in this) {
        if (predicate(element)) {
            result.add(element)
        }
    }
    return result
}

fun isOdd(n: Int) = n % 2 != 0

// una operación intermedia de secuencia que deja pasar solo los elementos que cumplen el predicado
fun <T> Sequence<T>.keep(predicate: (T) -> Boolean): Sequence<T> = sequence {
    for (element in this@keep) {
        if (predicate(element)) yield(element)
    }
}

// una operación intermedia que transforma cada elemento: el equivalente de map
fun <T, R> Sequence<T>.transform(transformation: (T) -> R): Sequence<R> = sequence {
    for (element in this@transform) {
        yield(transformation(element))
    }
}

Solo cuando la operación terminal [forEach] solicita los elementos se ejecuta el predicado, y las pruebas se alternan con las salidas de [forEach]: cada elemento recorre toda la cadena antes de que entre el siguiente. Esta es la ejecución diferida (o perezosa) de las secuencias, igual que la de los streams de Java. La etiqueta [this@keep] designa al receptor de la función de extensión [keep], es decir, la secuencia original: sin etiqueta, [this] designaría al receptor de la lambda en [sequence], ya que esa lambda es una lambda con receptor. Solo es utilizable gracias a la evaluación perezosa: [take(5)] solicita únicamente los cinco primeros elementos, y solo esos se calculan. La lambda pasada a [transform] muestra cada potencia con la forma [2^n=value] ([countTrailingZeroBits] cuenta los ceros más a la derecha en la representación binaria, es decir, el exponente).

En las colecciones, estas funciones son [inline] e inmediatas; en las secuencias, conservan las lambdas y calculan los elementos solo cuando los solicita la operación terminal.

    7.8. Árboles de expresión

    Algunos lenguajes, como C#, permiten convertir una lambda no en código ejecutable, sino en una estructura de datos que la describe (un “árbol de expresión”): un programa puede entonces analizar la lambda [t => t.Limit > 20000] y traducirla, por ejemplo, a una cláusula SQL [WHERE limits > 20000] ejecutada por el servidor de base de datos.

    Kotlin, como Java, no tiene un equivalente: una lambda de Kotlin siempre se compila en código ejecutable; se puede llamar, pero no se puede examinar su funcionamiento interno. Sin embargo, varias herramientas se acercan:

    • Las referencias a propiedades: [Person::age] es un objeto ([KProperty1<Person, Int>]) que conoce el nombre de la propiedad ([Person::age.name]) y su tipo. Una biblioteca puede aprovechar esto para construir una consulta sin escribir una cadena: eso es lo que hace Spring Data MongoDB, por ejemplo, con sus extensiones de Kotlin, que permiten escribir un criterio como [Person::age gt 18];
    • Los DSL internos (“lenguajes específicos de dominio”): gracias a las lambdas con receptor, a las funciones [infix] y a la sobrecarga de operadores, una biblioteca de Kotlin puede ofrecer una sintaxis similar a SQL, que el programa ejecuta para construir una estructura de datos que describe la consulta. Este es el principio de la biblioteca Exposed, de JetBrains: [Brackets.selectAll().where { Brackets.limit greater 20000 }];
    • los complementos del compilador: el compilador de Kotlin puede extenderse con complementos que transforman el código. Así funciona kotlinx.serialization, los complementos [all-open] y [no-arg] utilizados con Spring y Hibernate, o el complemento [power-assert], que analiza la expresión de una aserción para mostrar sus detalles en caso de fallo. Sin embargo, se trata de herramientas de desarrollo, no de características integradas del programa.

    Hibernate, que veremos en el capítulo 11, ofrece las mismas soluciones que en Java: un lenguaje de consulta similar a SQL pero expresado en términos de clases y propiedades, HQL (["from Bracket t where t.limit > 20000"]), y la API Criteria de Jakarta Persistence, que construye la consulta mediante llamadas a métodos ([cb.gt(t.get("limit"), 20000)]). En ambos casos, la consulta son datos (una cadena o un árbol de objetos) que Hibernate traduce a SQL, mientras que una lambda pasada a [filter] se ejecuta dentro del programa Kotlin.

    7.9. Conclusión

    Puntos clave de este capítulo:

    • En Kotlin, las funciones son valores: tienen un tipo funcional ([(Int, Int) -> Int], [() -> Unit], [(T) -> Boolean], [(() -> Unit)?], [T.() -> R]…), pueden almacenarse en variables, pasarse como parámetros, devolverse como resultados y llamarse como funciones ordinarias. Para la máquina virtual, son objetos que implementan las interfaces [Function0], [Function1]…;
    • las interfaces de [java.util.function] ([Function], [Supplier], [Consumer], [Predicate]…), junto con [Runnable], [Callable] y [Comparator], siguen siendo utilizables: cuando un método de Java espera una interfaz funcional, Kotlin convierte automáticamente una lambda o una referencia a ella (conversión SAM); en otros casos, la conversión se escribe de forma explícita: [Comparator { … }];
    • para nombrar un tipo de función, disponemos del alias [typealias] (simplemente un alias) y de [fun interface] (un verdadero tipo nuevo, implementable mediante una lambda);
    • una función puede obtenerse mediante una expresión lambda ([{ a, b -> a + b }], [{ it * it }], escrita fuera de los paréntesis cuando es el último parámetro, y cerrada con [return@label]), mediante una función anónima, mediante un objeto anónimo, o mediante una referencia ([::function], [object::method], [Class::method], [::Class]). Dos referencias a la misma función del mismo objeto son iguales; dos lambdas nunca lo son;
    • las lambdas capturan las variables que las rodean, incluidas las [var], que pueden modificar (el compilador las almacena en objetos [Ref]); entonces ven el valor de la variable en el momento de su ejecución, lo que exige precaución en los bucles y entre hilos;
    • las funciones que devuelven funciones y las extensiones sobre tipos funcionales ([then], [and], [or]…) componen nuevas funciones; [compareBy], [thenBy] y [reversed] construyen comparadores;
    • las funciones [inline] copian su código y el de las lambdas en el sitio de la llamada, sin objeto ni conversión, y permiten retornos no locales; [noinline] y [crossinline] tratan casos especiales. Las funciones de ámbito [let], [run], [with], [apply] y [also] son las aplicaciones más comunes de esto;
    • se elige un tipo funcional para comportamientos breves y puntuales; una [fun interface] para un tipo distinto o una API que pueda usarse desde Java; una interfaz con varios miembros (o una interfaz “de negocio”) para un rol de la aplicación;
    • un evento se implementa mediante el patrón de escuchas: una clase [XxxEvent], un tipo de escucha (a menudo un [typealias] de tipo funcional), [addXxxListener] / [removeXxxListener], y una lista de funciones ([CopyOnWriteArrayList]) recorrida por un método [fireXxx]. Las propiedades delegadas [Delegates.observable] y [Delegates.vetoable] señalan o filtran los cambios de una propiedad, y [PropertyChangeSupport] administra por ellas la lista de escuchas;
    • las operaciones de colecciones (inmediatas, [inline]) y las operaciones de secuencias (perezosas) son funciones de orden superior; Kotlin no tiene árboles de expresión, e Hibernate expresa sus consultas mediante HQL o la API Criteria.

    Las lambdas reaparecerán en todos los capítulos siguientes: un hilo ejecuta una lambda ([thread { … }]), y un [ExecutorService] ejecuta un [Callable] (capítulo 8); una corrutina se lanza con [launch { … }] o [async { … }] (capítulo 9), las funciones de extensión de [ResultSet] recibirán, en forma de lambda, la transformación de una fila del resultado en un objeto (capítulo 10), y los servicios web de Spring Boot procesan las solicitudes HTTP en métodos que el framework llama como escuchas (capítulo 13).
